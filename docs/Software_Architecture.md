## 1 概述
### 1.1 设计目标
本软件基于 STM32F103ZET6 硬件平台与 FreeRTOS 实时操作系统，实现车身控制模块核心功能。

系统主要实现功能如下：
- 灯光控制
- 门锁控制
- 环境光采集与自动灯光功能
- CAN 总线通信交互
- 故障检测与故障诊断
- 故障日志存储与读取
- 本地人机交互处理
- 系统状态统一管理

软件设计遵循**分层解耦、模块化设计、事件驱动、状态集中管理、高内聚低耦合**原则，使系统具备良好的可维护性、扩展性和工程化特征。

### 1.2 设计原则
1. **分层解耦原则**
系统采用 **应用层 → 服务层→ 驱动层→ HAL硬件抽象层 → 硬件** 五级分层架构，层级自上而下依赖：
- **应用层**：负责所有业务逻辑与控制策略实现。
- **服务层**：提供通用功能服务，不包含具体业务逻辑。
- **驱动层**：完成硬件外设抽象封装，提供统一硬件操作接口。

严格禁止跨层非法调用：
- 禁止应用层直接调用 HAL 接口；
- 禁止服务层包含业务控制策略；
- 禁止驱动层掺杂业务逻辑判断。

1. **实时性原则**
系统基于 FreeRTOS 抢占式多任务调度，根据业务实时性差异分级分配任务优先级：
- CAN 通信高优先级任务，保障远程控制指令低延迟响应；
- 执行器控制任务，保障灯光、门锁输出实时性；
- 故障检测任务实时轮询，快速捕获系统异常；
- 日志、存储等非关键任务采用低优先级后台运行，不抢占关键业务资源。

1. **可靠性原则**
系统多重机制保障车载级运行可靠性：
- 所有控制与故障检测配备**软件防抖机制**，滤除瞬时干扰；
- 核心功能采用**状态机管理**，避免逻辑混乱；
- 独立看门狗实时监控系统运行，异常自动复位；
- 支持 CAN 总线离线检测与自动恢复机制；
- Flash 故障日志添加数据校验，保证存储数据可靠有效。

1. **可扩展性原则**：
系统所有模块均采用标准化接口设计，模块间低耦合通信：
- 新增功能无需修改底层驱动与核心框架；
- 原有业务逻辑不受新增功能影响；
- 功能扩展仅通过新增应用层、服务层模块即可实现，具备良好迭代能力。

1. **优先级仲裁原则**
系统控制优先级如下：
`远程CAN指令 > 本地手动按键 > 自动灯光逻辑` 
当多个控制源同时存在时：
高优先级事件覆盖低优先级事件。

## 2 整体软件架构
### 2.1 三层软件架构
系统采用标准三层架构，各层职责单一，依赖关系自上而下，底层不依赖上层业务。

| 层级 | 核心职责 | 包含模块 | 
| ---- | ---- | ---- | 
| 应用层 | 业务逻辑编排，实现BCM核心控制策略 | 灯光管理、门锁管理、迎宾灯光、系统状态管理、故障联动 | 
| 服务层 | 通用基础能力封装，提供与业务无关的通用组件 | 按键管理、信号滤波、故障管理、CAN协议解析、存储管理、日志服务 | 
| 驱动层 | 硬件外设抽象封装，提供统一硬件读写接口 | GPIO、ADC、CAN、UART、SPI Flash、RTC、IWDG | 
### 2.2 FreeRTOS系统调度架构
基于FreeRTOS抢占式多任务调度机制，按业务实时性要求划分任务优先级，通过消息队列、软件定时器、互斥锁实现任务间通信与资源保护。
- **高优先级**：CAN通信任务、故障检测任务，保障指令响应与故障上报实时性
- **中优先级**：传感器采集任务、按键检测任务
- **低优先级**：执行器输出任务、人机交互任务、日志存储任务
- **系统级**：软件定时器驱动心跳周期报文，保证时序精度不受任务阻塞影响

### 2.3 软件数据流设计
#### 2.3.1 CAN 控制指令数据流
```
        CAN总线物理信号
              │
              ▼
    CAN Driver (驱动层)── 中断接收原始帧
              │
              ▼
      CAN_Message 接收队列
              │
              ▼
    CAN Protocol (服务层) ── DLC校验、值域校验、防抖校验
              │
              ▼
    控制指令事件队列
              │
              ▼
        执行器控制任务
              │
              ▼
    状态管理中心 ── 更新目标状态
              │
              ▼
    GPIO Driver (驱动层)
              │
              ▼
        继电器硬件输出
              │
              ▼
    触点回读采集 ── 故障检测任务校验
              │
              ├─ 一致 → 状态报文上报
              └─ 不一致 → 故障事件上报
```
#### 2.3.2 本地按键数据流
```
        按键硬件输入
              │
              ▼
    GPIO Driver (BSP层)
              │
              ▼
    Sensor_Key_Task (轮询扫描)
              │
              ▼
    按键状态机 ── 防抖、长短按识别
              │
              ▼
      Key_Event 事件队列
              │
              ▼
    应用层业务模块 ── 优先级仲裁后执行
              │
              ▼
        状态更新与输出
```
#### 2.3.3 故障检测与存储数据流
```
    各硬件采集点 / 总线状态
              │
              ▼
    Fault_Task (周期检测)
              │
              ▼
    故障防抖判定
              │
              ├─ 新故障激活 → 故障事件队列
              │                     │
              │                     ▼
              │               状态中心更新
              │                     │
              │                     ├─ CAN故障报文上报
              │                     └─ 声光报警输出
              ▼
        Storage_Task
              │
              ▼
    Flash环形故障日志存储
```

## 3 驱动层详细设计
### 3.1 驱动层设计目标
**1.核心职责**
- 封装 HAL 库，完成全部外设初始化；
- 统一硬件读写接口，屏蔽引脚、寄存器差异；
- 硬件改动仅修改驱动层代码，上层代码无需调整；    
- 提供硬件状态查询能力；
- 上电默认电平、异常硬件安全兜底。  

**2.设计原则**
- 单一职责：一个文件只对应一类硬件，硬件收发与协议解析分开写。
- 无业务：只做电平 / 数据读写，不做灯光、故障、指令等业务判断。
- 接口稳定：上层只调用对外 API，底层硬件改动不影响上层代码。

### 3.2 驱动层软件结构
```
BSP/
├── bsp_gpio.c/h
├── bsp_adc.c/h
├── bsp_can.c/h
├── bsp_uart.c/h
├── bsp_flash.c/h
├── bsp_rtc.c/h
└── bsp_iwdg.c/h
```
### 3.3 GPIO 驱动模块
#### 3.3.1 功能描述
负责所有数字 IO 资源的管理与抽象，涵盖输出类与输入类两类硬件：
   - 输出类：灯光继电器、门锁继电器、RGB 指示灯、有源蜂鸣器；
   - 输入类：本地按键、继电器触点回读引脚。  
  
模块提供统一的电平读写、翻转接口，上层通过设备枚举体访问对应 IO，无需感知具体引脚与端口。

#### 3.3.2 硬件资源
| 功能标识     | 对应引脚 | IO 方向 | 有效电平                 |
| ------------ | -------- | ------- | ---------------------- |
| RELAY_LIGHT  | PC5      | 输出    | 高电平触发继电器吸合     |
| RELAY_LOCK   | PC2      | 输出    | 高电平触发继电器吸合     |
| FB_LOCK      | PC3      | 输入    | 高电平表示触点闭合       |
| FB_LIGHT     | PC4      | 输入    | 高电平表示触点闭合       |
| BEEP         | PC0      | 输出    | 高电平触发蜂鸣器         |
| RGB_RED      | PB5      | 输出    | 低电平点亮               |
| RGB_GREEN    | PB0      | 输出    | 低电平点亮               |
| KEY1         | PA0      | 输入    | 高电平有效               |
| KEY2         | PC13     | 输入    | 高电平有效               |

#### 3.3.3 接口设计
```
void BSP_GPIO_Init(void);
void GPIO_WritePin(GPIO_ID id, uint8_t state);

```
#### 3.3.4 安全设计
系统上电初始化阶段，所有执行器类输出强制设置为安全默认状态：
- 灯光继电器、门锁继电器默认输出低电平，触点断开；
- 蜂鸣器默认输出低电平，关闭报警；
- RGB 指示灯默认熄灭，绿灯关闭、红灯关闭。

### 3.5 CAN驱动模块
#### 3.5.1 功能描述
负责 STM32 bxCAN 外设的初始化、过滤器配置与标准 CAN 帧收发，仅处理硬件层面的报文收发、过滤器管理与错误状态读取。报文 ID 解析、信号拆解、业务处理均由服务层 CAN 协议解析模块实现，BSP 层不感知报文内容与业务含义。

#### 3.5.2 硬件配置
| 参数项 | 配置值 |
| ------| ----- |
|CAN控制器|	CAN1 |
|接收引脚	|PB8（CAN_RX）|
|发送引脚	|PB9（CAN_TX）|
|工作模式	| 正常模式|
|通信速率	|250kbps|
|帧格式	|标准帧，11bit ID|
|采样点	|87.5%|

#### 3.5.3 CAN 消息结构
定义系统内统一的 CAN 消息结构体，所有 CAN 数据进入系统后均转换为该格式，作为中断、队列、协议层、应用层的统一数据载体。
```
typedef struct
{
    uint32_t id;          // 11位标准帧ID
    uint8_t  dlc;         // 数据长度码
    uint8_t  data[8];     // 8字节数据载荷
    uint32_t timestamp;   // 接收时间戳（ms）
} CAN_Message_t;
```
**接口说明：**
1. `BSP_CAN_Prepare()`：完成外设、引脚初始化，**不开启 CAN 控制器**；过滤器必须在 Start 之前配置完成。
2. `BSP_CAN_SetFilter()`：硬件过滤器配置接口，支持掩码模式，用于过滤总线上不需要的报文；**必须在 BSP_CAN_Start 调用前完成配置**，过滤器配置完成之后再启动 CAN 控制器。
3. `BSP_CAN_Start()`：使能 CAN 控制器，开始收发报文。
#### 3.5.4 接口设计
```
void BSP_CAN_Prepare(void);
uint8_t BSP_CAN_SetFilter(uint8_t bank,uint32_t id,uint32_t mask,uint8_t fifo); //设置CAN过滤器
void BSP_CAN_Start(void);
uint8_t CAN_SendMessage(CAN_Message_t *msg);    //发送一帧标准CAN报文
uint8_t CAN_ReceiveMessage(CAN_Message_t *msg); //读取接收队列中的一帧CAN报文
CAN_ErrorState_t CAN_GetErrorState(void);       //获取CAN控制器当前错误状态
```
#### 3.5.5 接收流程
CAN 接收采用「中断 + 队列」架构，保证实时性且避免中断上下文过长：
```
CAN RX 接收中断
        ↓
CAN硬件过滤器校验（硬件层过滤，丢弃不匹配报文）
        ↓
读取硬件FIFO，组装为CAN_Message_t
        ↓
写入FreeRTOS消息队列
        ↓
CAN Task 阻塞读取队列并处理
```
中断上下文严格限制操作范围，禁止执行以下操作：
- 报文协议解析、信号拆解；
- 修改全局业务状态；
- Flash 读写、串口打印等阻塞操作；
- 调用互斥锁、延时等 RTOS 阻塞 API。

### 3.9 独立看门狗驱动模块
#### 3.9.1 功能描述
提供系统异常自动复位能力，防止程序跑飞、任务卡死导致设备失控。仅提供基础的初始化与喂狗接口，喂狗策略与任务存活检测由上层系统管理模块实现。
#### 3.9.2 接口设计
```
void IWDG_Feed(void);  //看门狗喂狗，重置计数器
```
#### 3.9.3 使用原则
看门狗喂狗操作禁止由单个业务任务直接控制，System_Manager统一管理。
```
各任务周期上报存活状态
        ↓
System Manager 统一巡检所有任务状态
        ↓
全部任务正常 → 执行IWDG_Feed喂狗
        ↓
任务异常卡死 → 停止喂狗，触发看门狗复位
```
避免单任务死循环但仍持续喂狗，导致看门狗失效的问题。


### 3.10 BSP 单元测试模块
#### 3.10.1 功能描述
该模块属于开发调试辅助模块，不参与该项目业务逻辑运行。本模块基于 FreeRTOS 任务，完成 UART、GPIO、ADC、RTC、SPI‑Flash、CAN 共六组 BSP 底层驱动的验证工作。
测试用例包含外设正常功能测试与异常入参测试，覆盖空指针、非法 ID、非法地址等边界场景，用于快速验证驱动接口功能正确性与参数容错能力。全部测试执行完成后测试任务自动销毁，释放任务栈资源。
#### 3.10.2 接口设计
```
void BSP_UnitTestTask(void *argument)
```

#### 3.9.3 设计说明

1. **运行流程**
系统启动后由应用层创建`BSP_UnitTestTask`任务；任务内部完成 UART 初始化，串口输出测试日志，依次调用各个外设测试函数。每个测试函数内部先执行正常业务场景，再执行异常入参场景。全部用例跑完打印汇总信息，调用接口终止自身任务，不再占用 CPU 与栈资源。
2. **各模块测试要点**
- UART：测试字符串发送、格式化打印；传入 NULL 指针，校验驱动具备防护能力，系统不发生死机。
- GPIO：测试引脚置位、复位、翻转、输入电平读取；传入非法引脚 ID，验证驱动容错。
- ADC：多次采集原始采样值，校验采样结果处于 12 位 ADC 合理数值区间。
- RTC：预读丢弃上电瞬间不稳定时间戳，循环读取时间戳，校验时间戳持续递增。
- SPI‑Flash：使用空闲扇区执行擦除、页写入、读取，通过`memcmp`校验读写数据一致性；校验空指针、非法地址的返回值。
- CAN：支持两种测试方式：①Loopback 回环模式（芯片内部自发自收，无需外部硬件）；②正常模式，配合 CAN 调试器‑上位机进行外部收发测试；校验报文 ID、DLC、数据内容；接收前清空队列避免旧报文干扰，同时完成空指针等异常入参测试。

3. **依赖条件**
软件依赖各 BSP 驱动组件、FreeRTOS 任务与延时接口；
硬件依赖串口输出日志、指定测试 GPIO 引脚、Flash 空闲扇区；CAN 部分：回环模式仅需芯片本身；正常模式需要 CAN 调试器、CAN 总线接线，上位机配合手动收发报文。

## 4 服务层详细设计

### 4.1 服务层设计目标

服务层位于驱动层与应用层之间，负责提供通用的软件服务能力。

**服务层主要职责：**

**服务层特点：**

- 为Application提供稳定接口。

**软件结构：**
```
Service
├── can_protocol      // CAN协议解析与组包
├── key_manager       // 按键扫描与事件管理

└── log_service       // 统一日志服务
```

### 4.2 按键管理模块

- **功能**：实现两路独立按键的状态机扫描、软件防抖、长短按识别
- **防抖参数**：消抖时间20ms，长按判定阈值1000ms
- **事件输出**：短按事件、长按事件
- **对应按键逻辑**：
  - KEY1（PA0）：短按触发车灯开关切换，长按触发灯光工作模式（手动/自动）切换
  - KEY2（PC13）：短按触发门锁上锁/解锁切换，长按触发全部历史存储故障清除

#### 4.2.1 按键状态机
单个按键采用标准五态状态机实现：
```
   IDLE（空闲）
      ↓  检测到按下
   PRESS（按下）
      ↓  消抖计时
  DEBOUNCE（消抖）
      ↓  持续按下
   HOLD（长按中）
      ↓  检测到释放
  RELEASE（释放）
      ↓
    返回IDLE
```
#### 4.2.2 事件定义
采用事件队列方式输出按键事件。
```
typedef enum
{
    KEY1_SHORT = 0,    // KEY1短按事件
    KEY1_LONG,         // KEY1长按事件
    KEY2_SHORT,        // KEY2短按事件
    KEY2_LONG          // KEY2长按事件
} Key_Event_t;
```
#### 4.2.3 数据流
```
 GPIO 硬件输入
      ↓
Key Manager 模块
      ↓
Key Event Queue
      ↓
Application Task
```


### 4.3 信号滤波模块
#### 4.3.1 功能描述
负责 ADC 原始数据，均值采样，信号滤波、光照状态稳定判定、传感器异常检测。
输入： ADC 原始采样值
输出： 有效光照昼夜状态、传感器异常事件

#### 4.3.2 滑动平均滤波
采用 N 点滑动平均算法，公式如下：
`ADC_avg = (ADC₁ + ADC₂ + ... + ADCn) / n`

#### 4.3.3 光照滞回算法
设置双阈值滞回区间，避免临界点频繁切换。
| 状态判定 | ADC 数值范围 |
| -------- | ------------ |
| 黑夜     | ADC < 1600   |
| 白天     | ADC > 2800   |
| 中间区域 | 保持当前状态不变 |

#### 4.3.4 传感器异常判断
**异常判定条件：**
- ADC 采样值超出合法量程范围；
- 连续多次采样均为异常值。
**处理方式：**
- 输出传感器异常事件至故障管理模块；
- 光照状态保持上一有效值，不执行自动控制。

### 4.4 故障管理模块
#### 4.4.1 功能描述
- 故障状态统一管理；
- 故障防抖确认；
- 故障恢复判定；
- 故障事件通知分发；
- 运行期历史故障缓存。
  
#### 4.4.2 故障码定义
| 故障码 | 故障说明         |
| ------ | ---------------- |
| 0x01   | 传感器异常       |
| 0x02   | CAN 总线异常     |
| 0x03   | 灯光执行器故障   |
| 0x04   | 门锁执行器故障   |

#### 4.4.3 故障记录结构
```
typedef struct
{
    uint8_t  fault_code;    // 故障码
    uint8_t  status;        // 0x00=故障消除，0x01=故障激活
    uint32_t timestamp;     // 事件发生时间戳
    uint8_t  checksum;      // 校验字节
} Fault_Record;
```
#### 4.4.4 故障环形缓冲区
采用固定大小数组实现环形缓冲区, 写指针循环覆盖。
```
#define FAULT_BUFFER_SIZE   32
Fault_Record_t fault_buffer[FAULT_BUFFER_SIZE];
uint8_t fault_write_index;
```
#### 4.4.5 故障确认机制
所有故障均采用防抖确认机制，瞬时波动不触发故障。
**故障激活流程：**
```
异常条件产生
    ↓
  防抖计数
    ↓
达到防抖阈值
    ↓
  故障激活
    ↓
发送故障事件
```
**故障消除流程：**
```
恢复条件满足
    ↓
  恢复计数
    ↓
达到恢复阈值
    ↓
  故障清除
    ↓
发送故障事件
```
#### 4.4.6 故障事件结构
故障状态变更时，通过事件队列通知上层与存储模块。
```
typedef struct
{
    uint8_t fault_code;    // 故障码
    uint8_t event;         // FAULT_ACTIVE / FAULT_CLEAR
} Fault_Event;
```

### 4.5 CAN协议解析模块
#### 4.5.1 功能描述
- CAN 接收报文解析；
- 信号有效性检查；
- 控制指令转换输出；
- 状态 / 故障报文组包；
- CAN 通信异常基础处理。
  
#### 4.5.2 软件数据流
**接收流程：**
```
CAN 总线
↓
BSP CAN 驱动
↓
CAN 接收队列 (CAN_Message)
↓
CAN 协议任务
↓
CAN 指令队列 (CAN_Command)
↓
应用层任务
```
**发送流程：**
```
应用层
↓
状态变更事件
↓
CAN 协议组包
↓
CAN 发送队列 / 直接发送
↓
CAN 驱动
↓
CAN 总线
```
#### 4.5.3 数据结构定义
系统内部统一 CAN 消息结构体：
```
typedef struct
{
    uint32_t id;         // 11位标准帧ID
    uint8_t  dlc;        // 数据长度码
    uint8_t  data[8];    // 数据载荷
    uint32_t timestamp;  // 接收时间戳
} CAN_Message;
```
解析后的控制指令结构体：
```
typedef struct
{
    uint32_t msg_id;     // 原报文ID
    uint8_t  command;    // 指令类型
    uint8_t  value;      // 指令目标值
} CAN_Command;
```
#### 4.5.4 接收处理流程
CAN 协议任务从接收队列获取报文后，按以下四步依次处理：
**第一步：DLC 长度检查**
- 校验报文数据长度是否符合对应 ID 的规范定义；
- 非法长度报文直接丢弃，记录 DEBUG 日志。
**第二步：报文 ID 过滤**
- 仅处理合法指令 ID：0x011（灯光控制）、0x012（门锁控制）、0x013（故障清除）；
- 其他 ID 报文记录 DEBUG 日志后丢弃。   
**第三步：信号合法性检查**
- 按报文 ID 对应信号定义校验取值范围；
- 例如灯光控制指令仅 0x00（关闭）、0x01（开启）为合法值；
- 非法值报文视为无效，直接丢弃。
**第四步：生成控制事件**
- 校验全部通过后，组装为 CAN_Command_t 控制指令；
- 写入控制指令队列，交由应用层业务模块处理。

#### 4.5.5 CAN 发送设计
支持两种发送触发方式：
1. 周期发送
典型场景：设备心跳报文（ID:0x020，周期 2000ms）；
触发源：FreeRTOS 软件定时器回调；
定时器回调内读取当前系统状态，组包后调用 BSP 层接口发送。
2. 事件触发发送
典型场景：灯光状态变化、门锁状态变化、故障产生 / 消除；
触发源：应用层状态变更事件；
状态变化时调用协议组包接口，即时发送对应报文。


### 4.6 存储管理模块
#### 4.6.1 功能描述
- Flash 逻辑地址管理；
- 故障日志写入逻辑；
- 历史故障读取接口；
- 数据完整性校验。

#### 4.6.2 数据流
```
故障管理模块
      ↓
故障事件队列
      ↓
存储管理模块
      ↓
  Flash驱动
      ↓
W25Q64硬件存储
```

#### 4.6.3 存储策略
采用环形日志存储方案：
- Flash 内划分固定大小的日志存储扇区；
- 按顺序逐条写入故障记录；
- 存储空间写满后，自动覆盖最早的记录。

#### 4.6.4 数据校验
每条故障记录均包含校验字段：
- 记录内容：故障码、状态、时间戳、校验和；
- 读取时校验数据完整性；
- 校验失败的记录自动丢弃，避免异常数据导致逻辑错误。

### 4.7 日志服务模块
- **日志分级**：DEBUG、INFO、ERROR三级，可通过宏全局开关输出等级
  
| 等级  | 用途                                   |
| ----- | -------------------------------------- |
| DEBUG | 调试细节信息，开发阶段使用             |
| INFO  | 正常运行状态信息                       |
| ERROR | 错误与异常信息                         |
- **输出格式**：统一格式 `[时间戳] [等级] [模块名] 日志内容`
- **输出通道**：USART1串口输出，支持故障日志串口查询打印

### 5.3 BCM状态管理模块（bcm_state）
#### 5.3.1 设计目的
BCM状态管理模块用于维护系统统一运行状态。
解决多模块状态重复保存、状态不同步、状态访问混乱的问题。
#### 5.3.2 状态数据结构
```
typedef struct
{
    uint8_t light_state;    // 灯光状态
    uint8_t door_state;     // 门锁状态
    uint8_t work_mode;      // 系统工作模式
    uint8_t night_state;    // 昼夜环境状态
    uint8_t fault_level;    // 故障等级
}BCM_State;
```
#### 5.3.3 状态类型定义
**灯光状态**
```
typedef enum
{
    LIGHT_OFF,
    LIGHT_ON
}Light_State;
```
**门锁状态**
```
typedef enum
{
    DOOR_UNLOCK,
    DOOR_LOCK
}Door_State;
```
**系统模式**
```
typedef enum
{
    SYSTEM_NORMAL,
    SYSTEM_SAFE_MODE
}System_Mode;
```
#### 5.3.4 接口设计
```
BCM_State* BCM_GetState(void);   // 获取全局BCM状态（只读）
void BCM_SetLightState(Light_State state);  // 更新灯光状态

```
#### 5.3.5 访问规则
- 状态仅允许对应业务模块调用接口修改；其余模块仅做只读访问
- 多任务并发访问时，必须使用 Mutex 互斥锁保护
- 禁止业务模块直接读写BCM_State内部成员

### 5.4 灯光管理模块
- **工作模式**：支持手动模式、自动模式，KEY1长按切换
- **手动模式**：灯光状态仅响应CAN远程指令、本地KEY1短按
- **自动模式**：根据光照滞回判定结果自动开关灯；同时保留手动/CAN指令接管能力，指令优先级高于自动逻辑
- **执行校验**：每次输出控制后，延时稳定时间读取触点回读引脚（PC4），校验继电器实际状态；指令目标与回读状态不一致且持续防抖时间后，触发车灯故障（故障码0x03）
- **状态上报**：灯光状态发生变化时，触发车灯状态报文（ID:0x031）CAN上报
- **回读防抖**：触点回读信号软件防抖15ms

### 5.5 门锁管理模块
- **控制源**：响应CAN远程指令、本地KEY2短按，实现上锁/解锁切换
- **执行校验**：动作执行后读取触点回读引脚（PC3）校验，不一致且持续防抖后触发车锁故障（故障码0x04）
- **状态上报**：门锁状态变化时，触发门锁状态报文（ID:0x041）CAN上报
- **联动逻辑**：解锁事件触发迎宾灯光逻辑判断
- **回读防抖**：触点回读信号软件防抖15ms

### 5.6 迎宾灯光模块
- **触发条件**：门锁状态由上锁切换为解锁，且当前光照判定为黑夜
- **执行逻辑**：自动点亮近光灯，启动迎宾计时
- **优先级规则**：迎宾期间，手动按键、CAN指令可直接接管灯光控制权
- **结束逻辑**：计时结束后，恢复原灯光工作模式与自动灯光逻辑；迎宾计时期间不受门锁再次上锁影响

### 5.7 系统状态管理模块
- **模式管理**：维护系统两种运行模式
  - 正常模式：所有功能正常运行，RGB绿灯常亮
  - 故障模式：执行器全部断开，严重故障声光报警，保留本地按键与故障清除功能
- **上电自检**：上电依次完成时钟、GPIO、ADC、CAN、串口、Flash外设自检；自检失败直接进入故障模式
- **心跳管理**：周期上报设备心跳报文（ID:0x020），报文中携带当前系统工作模式
- **故障联动**：严重故障产生时自动切入故障模式；所有严重故障消除后恢复正常模式

## 6 FreeRTOS任务与调度设计
### 6.1 任务总表
| 任务名称       | 优先级 | 周期/触发   | 主要职责                         |
| -------------- | ------ | ----------- | -------------------------------- |
| CAN协议任务    | 5      | Queue阻塞   | CAN解析、协议处理                |
| 故障监控任务   | 4      | 10ms周期    | 故障检测、防抖                   |
| 输入采集任务   | 3      | 10ms周期    | ADC采集、按键扫描                |
| BCM控制任务    | 3      | 事件触发    | 灯光、门锁、迎宾逻辑             |
| 系统管理任务   | 2      | 50ms周期    | 模式管理、心跳、看门狗           |
| 日志存储任务   | 1      | 事件触发    | Flash写入、日志输出              |
### 6.2 软件定时器配置
周期报文由FreeRTOS软件定时器驱动，不受任务阻塞影响，保障时序容差指标。

| 定时器名称 | 周期 | 回调函数职责 | 容差要求 |
| ---- | ---- | ---- | ---- |
| 心跳报文定时器 | 2000ms | 组包并发送设备心跳报文 | ±80ms |

### 6.3 任务间通信机制
1. **消息队列**
   - CAN接收队列：CAN中断投递原始报文，接收任务读取解析
   - 指令队列：解析后的控制指令投递至执行器任务
   - 故障事件队列：故障检测模块投递故障事件，触发上报与存储
2. **互斥锁**
   - 全局状态互斥锁：保护系统工作模式、故障状态等共享资源
   - Flash操作互斥锁：保护SPI总线并发访问
3. **访问规则**：多任务共享变量必须通过临界区或互斥锁保护，禁止无保护并发读写

### 6.4 时序指标保障
严格匹配CAN通信协议时序规范：
- 状态变化事件报文：状态变更后 ≤20ms 完成发送
- 故障确认后报文：故障防抖确认后 ≤50ms 完成上报
- 指令响应：指令接收解析 ≤5ms，指令执行完成 ≤50ms，状态反馈 ≤100ms

## 7 核心业务流程
### 7.1 上电启动流程
1. 系统复位，HAL库初始化，系统时钟配置为72MHz
2. 外设驱动依次初始化：GPIO、ADC、CAN、UART、SPI、RTC、IWDG
3. FreeRTOS内核初始化，创建所有任务、队列、定时器、互斥锁
4. 加载Flash历史故障记录，初始化故障管理模块
5. 启动系统调度器，任务开始运行
6. 完成上电自检，自检通过进入正常模式；失败进入故障安全模式
7. 存在历史故障则上电首次上报故障状态报文

### 7.2 CAN控制指令处理流程
1. CAN外设收到报文，触发接收中断，将原始帧写入CAN接收队列
2. CAN接收任务被唤醒，读取报文并执行协议校验
3. 校验不通过：直接丢弃，记录错误日志
4. 校验通过：解析指令内容，投递至执行器控制任务
5. 执行器任务进行优先级仲裁，高优先级指令覆盖当前低优先级动作
6. 更新继电器输出电平，延时稳定后读取触点回读，校验执行结果
7. 状态发生变化时，触发对应状态报文上报；校验失败则触发故障上报

### 7.3 故障检测与处理流程
1. 故障检测任务周期轮询各异常条件
2. 异常条件触发时启动防抖计时，瞬时抖动自动清零
3. 持续异常达到防抖时间，确认故障激活
   - 更新故障状态位图
   - 投递故障事件，触发CAN故障报文（ID:0x003）上报
   - 写入Flash故障日志
   - 根据故障等级执行对应安全策略与报警
4. 异常条件消失，启动恢复防抖计时
5. 持续正常达到恢复时间，确认故障消除
   - 更新故障状态位图
   - 上报故障消除报文
   - 所有严重故障消除后，退出故障安全模式

### 7.4 自动灯光与迎宾灯光流程
1. 传感器任务周期采集光照ADC值，经滑动滤波后输出有效值
2. 滞回比较算法判定昼夜状态，状态变更时更新全局光照标志
3. 灯光管理模块判断当前模式：
   - 手动模式：不执行自动开关灯逻辑
   - 自动模式：根据昼夜状态自动切换灯光
4. 门锁解锁事件触发时：
   - 判定当前为黑夜则启动迎宾灯光，点亮车灯
   - 启动迎宾软件定时器，计时期间暂停自动灯光逻辑
   - 计时结束后恢复原灯光模式与自动控制逻辑

## 8 异常与可靠性设计
### 8.1 故障安全状态
系统进入故障安全模式时，强制执行以下状态：
- 所有继电器输出低电平，负载全部断开
- RGB红灯常亮，绿灯强制熄灭
- 蜂鸣器按严重故障节奏报警
- 保留本地按键功能与故障清除能力
- 周期心跳报文继续发送，工作状态字段更新为故障模式（0x01）

### 8.2 CAN总线异常处理
严格对齐CAN协议规范定义的三级错误状态与恢复流程：
- **主动错误状态**：TEC<127且REC<127，正常通信，无额外处理
- **被动错误状态**：TEC≥127或REC≥127，记录轻微故障，继续通信
- **总线关闭（Bus‑Off）**：
  1. 记录CAN总线严重故障（故障码0x02），执行器切入安全状态
  2. 尝试发送故障状态报文；总线无法发送时存入本地故障缓存
  3. 延时100ms后完整重新初始化bxCAN外设，清除错误计数器
  4. 初始化成功后恢复通信，上报故障消除报文
  5. 最多连续重试3次，失败则保持故障安全模式，等待系统复位

### 8.3 看门狗防护
- 独立看门狗溢出时间约1.5s，由系统状态任务统一喂狗
- 任务卡死、程序跑飞、硬fault等异常场景触发看门狗自动复位
- 复位后系统记录看门狗复位事件，便于问题追溯

### 8.4 数据可靠性
- Flash故障记录增加校验和，读取时校验完整性
- 全局共享资源全部加锁保护，避免多任务并发读写错乱
- 指令与故障均采用防抖机制，滤除瞬时干扰与误触发
