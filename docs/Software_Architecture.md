## 1 概述
### 1.1 设计目标
本软件基于 STM32F103ZET6 硬件平台与 FreeRTOS 实时操作系统，实现车身控制模块核心功能。

系统主要实现功能如下：
- 灯光控制
- 门锁控制
- 环境光采集与自动灯光功能
- CAN 总线通信交互
- 故障检测与故障诊断
- 故障日志存储与读取
- 本地人机交互处理
- 系统状态统一管理

软件设计遵循**分层解耦、模块化设计、事件驱动、状态集中管理、高内聚低耦合**原则，使系统具备良好的可维护性、扩展性和工程化特征。

### 1.2 设计原则
1.  **分层解耦与 OS 隔离原则**
系统采用四层软件分层架构：**应用层 → 服务层 → OSAL 操作系统抽象层 → 驱动层**，底层驱动再依赖 HAL 硬件库，形成完整五级依赖链：应用层 → 服务层 → OSAL → 驱动层 → HAL → 硬件。层级仅允许自上而下单向调用，禁止跨层逆向、越级非法调用。

- **应用层 (App)**：负责所有车身业务逻辑、任务创建与调度管理，实现 BCM 控制策略；仅调用服务层对外接口，不直接操作硬件、不调用原生 FreeRTOS API。
- **服务层 (Service)**：提供与业务无关的通用基础组件；仅通过 OSAL 抽象接口完成多任务同步，不直接依赖 FreeRTOS 原生函数。
- **OSAL 操作系统抽象层**：唯一收拢全部 FreeRTOS 原生 API、内核句柄（队列、互斥锁、任务、延时）；对外提供统一 OS 通用接口。
- **驱动层 (BSP)**：纯硬件外设抽象封装，仅提供硬件读写接口；禁止包含任何操作系统相关代码、队列、互斥锁、任务同步逻辑，硬件中断仅完成本地缓存拷贝，不调用 OS 接口，完全裸机兼容。

分层禁止行为：
- 禁止应用层直接调用 OSAL、驱动层、HAL 接口；
- 禁止服务层嵌入业务控制逻辑、直接调用 FreeRTOS 原生函数；
- 禁止驱动层掺杂业务判断、多任务缓冲、资源互斥、RTOS 相关代码；
- 禁止 OSAL 层出现硬件读写、车身业务逻辑。

1. **实时性原则**
系统基于 FreeRTOS 抢占式多任务调度，根据业务实时性差异分级分配任务优先级：
- CAN 通信高优先级任务，保障远程控制指令低延迟响应；
- 执行器控制任务，保障灯光、门锁输出实时性；
- 故障检测任务实时轮询，快速捕获系统异常；
- 执行器输出、人机交互、日志存储等非关键任务采用低优先级后台运行，不抢占关键业务资源。
- 所有心跳报文由 FreeRTOS 软件定时器驱动，时序精度不受任务阻塞影响。

1. **可靠性原则**
系统多重机制保障车载级运行可靠性：
- 所有控制与故障检测配备**软件防抖机制**，滤除瞬时干扰；
- 核心功能采用**状态机管理**，避免逻辑混乱；
- 独立看门狗实时监控系统运行，异常自动复位；
- 支持 CAN 总线离线检测与自动恢复机制；
- Flash 故障日志添加数据校验，保证存储数据可靠有效。
- 多任务共享资源通过 OSAL 互斥锁保护，临界区最小化，防止数据错乱、优先级反转。

1. **可扩展性与可移植性原则**
系统全模块标准化接口设计，模块间低耦合通信，同时兼顾操作系统移植能力：
- 新增车身附属功能仅扩展应用层、服务层模块，无需修改 OSAL、底层驱动核心框架；
- OSAL 层统一封装操作系统接口，更换 FreeRTOS、AUTOSAR OS、VxWorks 等实时操作系统仅修改 OSAL 内部实现，上层服务、应用代码无需重构；
- 硬件引脚、外设变更仅改动驱动层 BSP 代码，上层业务完全不受影响。

## 2 整体软件架构
### 2.1 四层软件架构
系统采用标准四层架构，各层职责单一，依赖关系自上而下，底层不依赖上层业务。

| 层级 | 核心职责 | 包含模块 | 
| ---- | ---- | ---- | 
| 应用层 | 业务逻辑编排，实现BCM核心控制策略 | 灯光管理、门锁管理、迎宾灯光、系统状态管理、故障联动 | 
| 服务层 | 通用基础能力封装，通过 OSAL 接口完成多任务同步；核心算法支持裸机独立运行 | 按键管理、信号滤波、故障管理、CAN协议解析、存储管理、日志服务、执行器回读诊断 | 
|OSAL | 操作系统抽象层收拢全部 FreeRTOS 原生 API；封装队列、互斥锁、延时、任务通用接口 | FreeRTOS各函数封装 |
| 驱动层 | 硬件外设抽象封装，提供统一硬件读写接口 | GPIO、ADC、CAN、UART、SPI Flash、IWDG | 

### 2.2 FreeRTOS系统调度架构
基于 FreeRTOS 抢占式多任务调度机制，按业务实时性划分任务优先级，任务间通信、资源保护全部通过 OSAL 封装接口实现，禁止上层直接调用 FreeRTOS 原生 API。
- **高优先级**：CAN协议任务、故障监控任务，保障指令响应与故障上报实时性
- **中优先级**：输入采集任务、BCM控制任务
- **低优先级**：系统管理任务、故障处理任务
- **系统级**：软件定时器驱动心跳周期报文，保证时序精度不受任务阻塞影响

任务间通信组件统一约束：

1. 消息队列、互斥锁、信号量等内核对象仅在 OSAL 层定义封装，句柄在对应服务层内部实例化；
2. 硬件中断上下文仅执行硬件数据拷贝，禁止调用任何阻塞型 OS 接口，同步通知交由后台任务处理；
3. 多任务共享串口、SPI Flash 等硬件资源时，通过 OSAL 互斥锁做资源保护，缩短锁持有时间。

## 3 驱动层详细设计
### 3.1 驱动层设计目标
**1.核心职责**
- 封装 HAL 库，完成全部外设初始化；
- 统一硬件读写接口，屏蔽引脚、寄存器差异；
- 硬件改动仅修改驱动层代码，上层代码无需调整；    
- 提供硬件状态查询能力；
- 上电默认电平、异常硬件安全兜底。  

**2.设计原则**
- 单一职责：一个文件只对应一类硬件，硬件收发与协议解析分开写。
- 无业务：只做电平 / 数据读写，不做灯光、故障、指令等业务判断。
- 接口稳定：上层只调用对外 API，底层硬件改动不影响上层代码。

### 3.2 驱动层软件结构
```
BSP/
├── bsp_gpio.c/h
├── bsp_adc.c/h
├── bsp_can.c/h
├── bsp_uart.c/h
├── bsp_flash.c/h
└── bsp_iwdg.c/h
```

### 3.3 GPIO 驱动模块
#### 3.3.1 功能描述
负责所有数字 IO 资源的管理与抽象，涵盖输出类与输入类两类硬件：
   - 输出类：灯光继电器、门锁继电器、RGB 指示灯、有源蜂鸣器；
   - 输入类：本地按键、继电器触点回读引脚。  
  
模块提供统一的电平读写、翻转接口，上层通过设备枚举体访问对应 IO，无需感知具体引脚与端口。

#### 3.3.4 安全设计
系统上电初始化阶段，所有执行器类输出强制设置为安全默认状态：
- 灯光继电器、门锁继电器默认输出无效电平，触点断开；
- 蜂鸣器默认输出无效电平，关闭报警；
- RGB 指示灯默认熄灭，绿灯关闭、红灯关闭。

### 3.5 CAN驱动模块
#### 3.5.1 功能描述
负责 STM32 bxCAN 外设的准备、过滤器配置、硬件启动停止、标准 CAN 帧原始发送、接收事件上报、控制器错误状态读取。
> BSP 层职责边界：仅操作硬件外设，不实现软件消息队列、不做报文缓存；收到报文通过函数指针回调通知上层服务模块。报文缓存、队列、超时接收、ID 解析、信号拆解、业务处理全部交由服务层 CAN 模块实现；BSP 不感知报文业务含义。

#### 3.5.2 硬件配置
| 参数项 | 配置值 |
| ------| ----- |
|CAN控制器|	CAN1 |
|接收引脚	|PB8（CAN_RX）|
|发送引脚	|PB9（CAN_TX）|
|工作模式	| 正常模式|
|通信速率	|250kbps|
|帧格式	|标准帧，11bit ID|
|采样点	|87.5%|

#### 3.5.3 CAN 消息结构
定义系统内统一的 CAN 消息结构体，所有 CAN 数据进入系统后均转换为该格式，作为中断、队列、协议层、应用层的统一数据载体。
```
typedef struct
{
    uint32_t id;          // 11位标准帧ID
    uint8_t  dlc;         // 数据长度码
    uint8_t  data[8];     // 8字节数据载荷
    uint32_t timestamp;   // 接收时间戳（ms）
} CAN_Message_t;
```
回调函数指针类型定义：
`typedef void (*BSP_CAN_RxCallback_t)(const CAN_Message_t *p_msg);`
#### 3.5.4 接口设计
```
void BSP_CAN_Prepare(void);
void BSP_CAN_RegisterRxCallback(BSP_CAN_RxCallback_t cb);          //注册接收事件回调
uint8_t BSP_CAN_SetFilter(uint8_t bank,uint32_t id,uint32_t mask,uint8_t fifo); //硬件过滤器配置
void BSP_CAN_Start(void);                                           //启动CAN控制器，使能接收中断
void BSP_CAN_Stop(void);                                            //停止CAN控制器，关闭接收中断
uint8_t BSP_CAN_SendRawMessage(const CAN_Message_t *msg);           //底层原始报文发送
CAN_ErrorState_t BSP_CAN_GetErrorState(void);                       //获取CAN控制器硬件错误状态
```
**接口说明：**
1. `BSP_CAN_Prepare()`：完成外设、引脚初始化，**不开启 CAN 控制器**；过滤器必须在 Start 之前配置完成。
2. `BSP_CAN_SetFilter()`硬件过滤器**必须在`BSP_CAN_Start()`之前调用配置**；
3. 启动前需要调用`BSP_CAN_RegisterRxCallback()`注册接收回调函数，否则收到报文直接丢弃。
   
  
### 3.6 UART 驱动模块
#### 3.6.1 功能描述
负责串口调试通道的 BSP 硬件驱动封装，仅完成底层硬件收发能力：
- 向上层服务层提供原始阻塞发送、阻塞接收硬件接口；
- 不实现格式化、多任务互斥保护、数据缓存逻辑；
- 上层基于本驱动实现系统分级调试日志输出、故障信息打印、运行状态观测与问题定位。

本串口仅作为调试通道，不承载核心业务数据传输。

#### 3.6.2 硬件配置

| 参数项   | 配置值                          |
| -------- | ------------------------------ |
| 外设接口 | USART1                          |
| 发送引脚 | PA9（TX）                       |
| 接收引脚 | PA10（RX）                      |
| 波特率   | 115200                          |
| 数据格式 | 8 数据位、无校验、1 停止位        |

#### 3.6.3 接口设计
```
void BSP_UART_Init(void);                          //串口BSP占位初始化，硬件初始化由CubeMX完成
int BSP_UART_RawSend(const uint8_t *buf, uint16_t len, uint32_t timeout);  //底层阻塞发送
int BSP_UART_RawRecv(uint8_t *buf, uint16_t len, uint32_t timeout);        //底层阻塞接收

```

#### 3.7.1 功能描述
负责 W25Q64 SPI Flash 芯片的底层读写擦除驱动，仅提供物理地址层面的访问接口。

#### 3.7.2 硬件资源

| 功能         | 对应引脚 | SPI 参数             |
| ------------ | -------- | ------------------- |
| NSS 片选     | PA4      | 模式：全双工主模式    |

#### 3.7.3 接口设计
驱动接口采用状态返回机制，统一反馈硬件操作结果。
```
typedef enum
{
    BSP_FLASH_OK = 0U,
    BSP_FLASH_ERR_SPI,
    BSP_FLASH_ERR_TIMEOUT,
    BSP_FLASH_ERR_PARAM,
} BSP_Flash_StatusTypeDef;
```


底层实现硬件级可靠性保障：
- Busy状态检测；
- 写完成等待；
- SPI错误反馈
- 参数校验检查
- 超时保护

### 3.8 独立看门狗驱动模块
#### 3.8.1 功能描述
提供系统异常自动复位能力，防止程序跑飞、任务卡死导致设备失控。仅提供基础的初始化与喂狗接口，任务存活监控、喂狗决策逻辑交由上层系统管理模块实现。
#### 3.8.2 接口设计
```
void IWDG_Feed(void);  //看门狗喂狗，重置计数器
```
#### 3.8.3 使用原则
1. 底层 IWDG 驱动仅负责硬件操作，**业务任务禁止直接调用 IWDG_Feed**，喂狗动作统一由 SystemManageTask 执行。
2. 多任务存活监控机制：
```
可监控任务周期性向上层上报心跳（存活标记）
        ↓
SystemManageTask周期巡检已纳入监控的任务心跳状态
        ↓
所有被监控任务均正常存活 → 调用IWDG_Feed执行喂狗
        ↓
任一被监控任务卡死/停止上报心跳 → 停止喂狗，等待IWDG硬件超时触发系统复位
```
3. 设计目的：规避单一业务任务卡死，但仍然持续喂狗，造成看门狗失效的风险。
4. 边界约定：阻塞型任务（CAN 协议任务、故障处理任务）不参与心跳上报，系统不会对这两个任务做存活检测，不因为这两个任务阻塞而触发看门狗复位。


### 3.9 BSP 单元测试模块
#### 3.9.1 功能描述
该模块属于开发调试辅助模块，不参与该项目业务逻辑运行。本模块基于 FreeRTOS 任务，完成 UART、GPIO、ADC、RTC、SPI‑Flash、CAN 共六组 BSP 底层驱动的验证工作。
测试用例包含外设正常功能测试与异常入参测试，覆盖空指针、非法 ID、非法地址等边界场景，用于快速验证驱动接口功能正确性与参数容错能力。全部测试执行完成后测试任务自动销毁，释放任务栈资源。
#### 3.9.2 接口设计
```
void BSP_UnitTestTask(void *argument)
```
#### 3.9.3 设计说明

1. **运行流程**
系统启动后由应用层创建`BSP_UnitTestTask`任务；任务内部完成 UART 初始化，串口输出测试日志，依次调用各个外设测试函数。每个测试函数内部先执行正常业务场景，再执行异常入参场景。全部用例跑完打印汇总信息，调用接口终止自身任务，不再占用 CPU 与栈资源。
2. **各模块测试要点**
- UART：测试字符串发送、格式化打印；传入 NULL 指针，校验驱动具备防护能力，系统不发生死机。
- GPIO：测试引脚置位、复位、翻转、输入电平读取；传入非法引脚 ID，验证驱动容错。
- ADC：多次采集原始采样值，校验采样结果处于 12 位 ADC 合理数值区间。
- RTC：预读丢弃上电瞬间不稳定时间戳，循环读取时间戳，校验时间戳持续递增。
- SPI‑Flash：使用空闲扇区执行擦除、页写入、读取，通过`memcmp`校验读写数据一致性；校验空指针、非法地址的返回值。
- CAN：支持两种测试方式：①Loopback 回环模式（芯片内部自发自收，无需外部硬件）；②正常模式，配合 CAN 调试器‑上位机进行外部收发测试；校验报文 ID、DLC、数据内容；接收前清空队列避免旧报文干扰，同时完成空指针等异常入参测试。

3. **依赖条件**
软件依赖各 BSP 驱动组件、FreeRTOS 任务与延时接口；
硬件依赖串口输出日志、指定测试 GPIO 引脚、Flash 空闲扇区；CAN 部分：回环模式仅需芯片本身；正常模式需要 CAN 调试器、CAN 总线接线，上位机配合手动收发报文。

## 4 OSAL操作系统抽象层详细设计
### 4.1 模块概述
OSAL（操作系统抽象层）用于隔离 Service 服务层、应用层与底层 FreeRTOS 内核。对上层封装任务、定时器、互斥锁、消息队列、系统时间、任务调度等 RTOS 能力，对外提供一套统一、与具体 RTOS 无关的抽象接口。
### 4.2 文件组成
| 文件 | 作用 |
| --- | --- |
| `osal/osal.h` | 对外头文件：类型定义、全部抽象接口声明，业务层唯一需要 include 的头 |
| `osal/osal.c` | OSAL 实现文件，内部包含 FreeRTOS 原生头，完成接口适配封装 |

### 4.3 数据类型定义（osal.h）
```
typedef void* osal_tick_t;
typedef void* osal_queue_t;               // OSAL抽象队列句柄
typedef void* osal_task_handle_t;         // OSAL抽象任务句柄
typedef void* osal_timer_handle_t;        // OSAL抽象定时器句柄

// 静态互斥锁结构体，内部缓冲区用于存放RTOS互斥锁控制块
#define OSAL_MUTEX_BUF_SIZE    (128U)
typedef struct
{
    __attribute__((aligned(4))) uint8_t buf[OSAL_MUTEX_BUF_SIZE];
    void *hdl;
} osal_mutex_t;
```

### 4.4 接口设计

统一返回约定：
|返回值|含义|
|---|---|
|1|执行成功|
|0|执行失败（入参非法（入参空指针、内存分配失败、超时、资源不足等）|

#### 4.4.1 互斥锁接口

用于多任务访问共享资源，例如串口打印，防止多任务输出乱码。

| 函数原型 | 功能说明 |
| --- | --- |
| `void osal_mutex_create(osal_mutex_t *m);` | 静态方式创建互斥锁，由上层传入预先分配好的 osal_mutex_t 结构体 |
| `uint8_t osal_mutex_take(osal_mutex_t *m, uint32_t ms);` | 获取互斥锁，ms 为超时时间 (ms)；OSAL_WAIT_FOREVER 代表永久等待 |
| `uint8_t osal_mutex_give(osal_mutex_t *m);` | 释放互斥锁 |
| `void osal_mutex_delete(osal_mutex_t *m);` | 销毁互斥锁，仅清空句柄；静态内存无需释放堆 |

#### 4.4.2 消息队列接口

用于任务与任务、中断与任务之间数据传递；CAN 模块接收报文使用。
| 函数原型 | 功能说明 |
| --- | --- |
| `osal_queue_t osal_queue_create(uint32_t count, uint32_t item_size);` | 创建消息队列；count：队列最大缓存个数，item_size：单条数据字节大小；失败返回 NULL |
| `uint8_t osal_queue_send(osal_queue_t q, const void *data, uint32_t ms);` | 任务上下文：向队列发送数据 |
| `uint8_t osal_queue_recv(osal_queue_t q, void *data, uint32_t ms);` | 任务上下文：从队列读取数据 |
| `uint8_t osal_queue_send_from_isr(osal_queue_t q, const void *data);` | 中断上下文专用：中断中写入队列，禁止任务上下文调用；内部自带任务切换处理 |
| `void osal_queue_delete(osal_queue_t q);` | 销毁队列，释放内核堆资源 |

#### 4.4.3 系统时间与周期延时接口

注意：带`from_isr`后缀接口可在中断上下文调用；其余时间 / 延时接口**仅允许任务上下文调用，禁止中断内使用**。
| 函数原型 | 功能说明 |
| --- | --- |
| `osal_tick_t osal_get_tick(void);` | 获取系统原生 tick 计数 |
| `uint32_t osal_get_ms(void);` | 获取系统毫秒时间戳，任务上下文调用 |
| `uint32_t osal_get_ms_from_isr(void);` | 中断上下文获取系统毫秒时间戳 |
| `void osal_msleep(uint32_t ms);` | 任务内毫秒阻塞延时（vTaskDelay 相对延时） |
| `void osal_delay_ms_until(osal_tick_t *last_wake_tick, uint32_t cycle_ms);` | 固定周期阻塞延时，底层基于`vTaskDelayUntil`，用于实现严格周期性任务 |

#### 4.4.4 软件定时器接口
实现说明：定时器创建时通过`pvPortMalloc`分配回调包装结构体，用于保存用户回调函数与入参；定时器销毁时同步释放该堆内存，避免内存泄漏。
| 函数原型 | 功能说明 |
| --- | --- |
| `uint8_t osal_timer_create(...);` | 创建 OSAL 软件定时器；uxAutoReload=1 自动重载，0 单次触发；handle_out 输出定时器句柄。 |
| `uint8_t osal_timer_start(osal_timer_handle_t handle);` | 启动定时器；**禁止在中断上下文调用** |
| `uint8_t osal_timer_stop(osal_timer_handle_t handle);` | 停止定时器；**禁止在中断上下文调用** |
| `uint8_t osal_timer_delete(osal_timer_handle_t handle);` | 删除定时器，释放定时器内核资源以及内部回调包装结构体堆内存 |

### 4.5 宏定义（osal.h 内部）

```
#define OSAL_WAIT_FOREVER    0xFFFFFFFFU   // 永久等待，锁、队列等待超时参数，单位ms
#define OSAL_MUTEX_BUF_SIZE  (128U)       // 静态互斥锁内存缓冲区大小
```
- `OSAL_WAIT_FOREVER`：接口入参，代表永久阻塞等待；
- `OSAL_MUTEX_BUF_SIZE`：静态互斥锁控制块缓冲区长度，用于静态分配互斥锁资源。

## 5 服务层详细设计

### 5.1 服务层设计目标

服务层位于驱动层与应用层之间，负责提供通用的软件服务能力。

**服务层主要职责：**
- CAN协议解析；
- 按键事件管理；
- 信号滤波处理；
- 故障诊断；
- 数据存储管理；
- 日志服务;
- 执行器回读诊断处理。
- 看门狗服务
  
**服务层特点：**
- 不直接操作硬件，所有硬件访问通过驱动层 BSP 接口完成；
- 不包含具体 BCM 业务策略；
- 所有多任务同步、消息队列、互斥锁均通过 **OSAL 抽象接口** 实现，**禁止直接调用 FreeRTOS 原生 API**；
- 核心算法（滤波、防抖、状态机）无操作系统绑定，支持裸机环境独立运行。

**软件结构：**
```
Service
├── executor_diag     // 执行器回读诊断
├── iwdg_service      // 看门狗服务
├── can_protocol      // CAN协议解析与组包
├── key_manager       // 按键扫描与事件管理
├── signal_filter     // 信号滤波与状态判定
├── fault_manager     // 故障诊断与状态管理
├── storage_manager   // 存储逻辑管理
└── log_service       // 统一日志服务
```

### 5.2 按键管理模块

- **功能**：实现两路独立按键的状态机扫描、软件防抖、长短按识别
- **防抖参数**：消抖时间20ms，长按判定阈值1000ms
- **事件输出**：短按事件、长按事件
- **对应按键逻辑**：
  - KEY1（PA0）：短按触发车灯开关切换，长按触发灯光工作模式（手动/自动）切换
  - KEY2（PC13）：短按触发门锁上锁/解锁切换，长按触发全部历史存储故障清除

`仅提供按键扫描处理函数与事件输出队列的操作接口，队列由上层通过 OSAL 创建`
#### 5.2.1 按键状态机
单个按键采用标准五态状态机实现：
```
   IDLE（空闲）
      ↓  检测到按下
   PRESS（按下）
      ↓  消抖计时
  DEBOUNCE（消抖）
      ↓  持续按下
   HOLD（长按中）
      ↓  检测到释放
  RELEASE（释放）
      ↓
    返回IDLE
```
#### 5.2.2 事件定义
采用事件队列方式输出按键事件。
```
typedef enum
{
    KEY1_SHORT = 0,    // KEY1短按事件
    KEY1_LONG,         // KEY1长按事件
    KEY2_SHORT,        // KEY2短按事件
    KEY2_LONG          // KEY2长按事件
} Key_Event_t;
```

### 5.3 信号滤波模块
#### 5.3.1 功能描述
负责 ADC 原始数据，均值采样，信号滤波、光照状态稳定判定、传感器异常检测。
输入： ADC 原始采样值
输出： **有效光照昼夜状态、传感器异常事件**

#### 5.3.2 滑动平均滤波
采用 N 点滑动平均算法，公式如下：
`ADC_avg = (ADC₁ + ADC₂ + ... + ADCn) / n`

#### 5.3.3 光照滞回算法
设置双阈值滞回区间，避免临界点频繁切换。
| 状态判定 | ADC 数值范围 |
| -------- | ------------ |
| 黑夜     | ADC < 1600   |
| 白天     | ADC > 2800   |
| 中间区域 | 保持当前状态不变 |

#### 5.3.4 传感器异常判断
**异常判定条件：**
- ADC 采样值超出合法量程范围；
- 连续多次采样均为异常值。
**处理方式：**
- 输出传感器异常事件至故障管理模块；
- 光照状态保持上一次有效值，不执行自动控制。

### 5.4 故障管理模块
#### 5.4.1 功能描述
- 接收全系统各模块上报的原始异常状态；
- 统一故障防抖确认、故障恢复判定逻辑；
- 故障状态变更后生成标准化故障事件，分发至上层队列；
- 对外提供故障状态查询接口，供业务模块读取当前故障激活情况。
  
`故障事件队列由上层通过 OSAL 创建，模块内部仅调用读写接口。`
  
#### 5.4.2 故障码定义
| 故障码 | 故障说明         |
| ------ | ---------------- |
| 0x01   | 传感器异常       |
| 0x02   | CAN 总线异常     |
| 0x03   | 灯光执行器故障   |
| 0x04   | 门锁执行器故障   |

#### 5.4.5 故障确认机制
所有故障均采用防抖确认机制，瞬时波动不触发故障。
**故障激活流程：**
```
业务模块上报异常状态
    ↓
  防抖计数
    ↓
达到防抖阈值
    ↓
  故障激活
    ↓
发送故障事件
```
**故障消除流程：**
```
业务模块上报正常状态
    ↓
  恢复计数
    ↓
达到恢复阈值
    ↓
  故障清除
    ↓
发送故障事件
```
#### 5.4.6 故障事件结构
故障状态变更时，通过事件队列通知上层与存储模块。
```
typedef struct
{
    uint8_t fault_code;    // 故障码
    uint8_t event;         // FAULT_ACTIVE / FAULT_CLEAR
} Fault_Event;
```

### 5.5 CAN协议解析模块
#### 5.5.1 功能描述
- CAN 接收报文解析；
- 信号有效性检查；
- 控制指令转换输出；
- 状态 / 故障报文组包；
- CAN 通信异常基础处理。

`仅提供协议解析任务入口，任务本身、收发队列由系统管理模块通过 OSAL 创建；`
#### 5.5.2 软件数据流
**接收流程：**
```
CAN 总线
↓
BSP_CAN 驱动（中断接收原始帧）
↓
BSP 接收回调函数（服务层注册）
↓
服务层将报文写入接收队列
↓
CAN 协议任务（从接收队列读取）
↓
CAN 指令队列 (CAN_Command)
↓
应用层任务
```
**发送流程：**
```
应用层
↓
状态变更事件
↓
CAN 协议组包
↓
CAN 发送队列 / 直接发送
↓
CAN 驱动
↓
CAN 总线
```
#### 5.5.3 数据结构定义
系统内部统一 CAN 消息结构体：
```
typedef struct
{
    uint32_t id;         // 11位标准帧ID
    uint8_t  dlc;        // 数据长度码
    uint8_t  data[8];    // 数据载荷
    uint32_t timestamp;  // 接收时间戳
} CAN_Message;
```
解析后的控制指令结构体：
```
typedef struct
{
    uint32_t msg_id;     // 原报文ID
    uint8_t  command;    // 指令类型
    uint8_t  value;      // 指令目标值
} CAN_Command;
```
#### 5.5.4 接收处理流程
CAN 协议任务从接收队列获取报文后，按以下四步依次处理：
**第一步：DLC 长度检查**
- 校验报文数据长度是否符合对应 ID 的规范定义；
- 非法长度报文直接丢弃，记录 DEBUG 日志。
**第二步：报文 ID 过滤**
- 仅处理合法指令 ID：0x011（灯光控制）、0x012（门锁控制）、0x013（故障清除）；
- 其他 ID 报文记录 DEBUG 日志后丢弃。   
**第三步：信号合法性检查**
- 按报文 ID 对应信号定义校验取值范围；
- 例如灯光控制指令仅 0x00（关闭）、0x01（开启）为合法值；
- 非法值报文视为无效，直接丢弃。
**第四步：生成控制事件**
- 校验全部通过后，组装为 CAN_Command_t 控制指令；
- 写入控制指令队列，交由应用层业务模块处理。

#### 5.5.5 CAN 发送设计
支持两种发送触发方式：
1. 周期发送
典型场景：设备心跳报文（ID:0x020，周期 2000ms）；
触发源：FreeRTOS 软件定时器回调；
系统管理模块通过 OSAL 创建维护，回调内仅调用 CAN 协议组包接口，服务层不直接操作定时器内核对象。
2. 事件触发发送
典型场景：灯光状态变化、门锁状态变化、故障产生 / 消除；
触发源：应用层状态变更事件；
状态变化时调用协议组包接口，即时发送对应报文。


### 5.6 存储管理模块
#### 5.6.1 功能描述
- Flash 逻辑地址管理；
- 故障日志写入逻辑；
- 历史故障读取接口；
- 数据完整性校验。

#### 5.6.2 数据流
```
故障管理模块
      ↓
故障事件队列
      ↓
存储管理模块
      ↓
  Flash驱动
      ↓
W25Q64硬件存储
```

#### 5.6.3 存储策略
采用**线性追加存储方案**：
- Flash 内划分固定大小的故障日志存储扇区；
- 故障记录按顺序逐条追加写入空闲槽；
- 每条记录附带校验和，识别掉电半写、Flash 干扰导致的数据损坏，读取时自动跳过非法记录；
- 存储空间写满后，执行整扇区擦除，清空全部历史故障记录，重新开始写入；
- 提供主动清除接口，上层业务可提前执行清理，避免写满瞬间批量丢失日志。

#### 5.6.4 数据校验
每条故障记录均包含校验字段：
- 记录内容：故障码、状态、时间戳、校验和；
- 读取时校验数据完整性；
- 校验失败的记录自动丢弃，避免异常数据导致逻辑错误。

### 5.7 日志服务模块
  
| 等级  | 用途                                   |
| ----- | -------------------------------------- |
| DEBUG | 调试细节信息，开发阶段使用             |
| INFO  | 正常运行状态信息                       |
| ERROR | 错误与异常信息                         |

- **日志分级**：DEBUG、INFO、ERROR三级，可通过宏全局开关输出等级
- **输出格式**：统一格式 `[时间戳] [等级] [模块名] 日志内容`
- **输出通道**：USART1串口输出，支持故障日志串口查询打印

日志串口输出的多任务互斥保护，通过 OSAL 互斥锁实现；日志服务模块仅调用 OSAL 加解锁接口，不直接操作内核互斥量。


### 5.8 执行器诊断模块
#### 5.8.1 功能描述
服务层执行器预处理诊断模块，用于车灯、车锁等执行器回读检测。读取BSP层软件输出命令与硬件回读反馈，对比期望输出和实际回读，输出原始采样状态送至 `fault_manager`。

#### 5.8.2 处理流程

1. 遍历待诊断执行器，调用 BSP 获取输出命令、硬件回读；
2. 对比期望输出与实际反馈，得到原始异常 / 正常状态；
3. 给故障管理模块提供原始状态数据。

### 5.9 看门狗服务模块
#### 5.9.1 模块概述
看门狗服务层基于底层 BSP 硬件 IWDG 驱动，实现**多任务心跳监控**。由系统管理任务 50ms 周期巡检；仅监控 4 个非阻塞业务任务；CAN 协议、故障处理任务为阻塞型任务，不纳入监控。所有被监控任务正常上报心跳才执行硬件喂狗，任一任务卡死则停止喂狗，最终硬件 IWDG 复位系统。
心跳计数数组采用 OSAL 静态互斥锁保护，防止多任务并发读写冲突。

### 5.9.2 对外接口
| 函数 | 功能 |
| --- | --- |
| `IWDG_Service_Init()` | 初始化互斥锁、清零计数与标记 |
| `IWDG_Service_TaskFeed(task_id)` | 任务上报心跳，清零对应计数器 |
| `IWDG_Service_TaskRoutine()` | 巡检入口，由系统管理任务 50ms 周期调用，判断超时、控制喂狗 |
### 5.9.3 使用约束

1. 巡检函数固定由系统管理任务 50ms 调用，修改周期需同步更新超时阈值。
2. 仅 4 个非阻塞任务调用`IWDG_Service_TaskFeed`上报心跳；阻塞任务不参与监控。
3. 互斥锁超时 10ms，获取锁失败直接放弃本次操作，规避死锁。
4. 计数器做上限钳位，防止 uint16_t 溢出造成误判。

## 6 应用层详细设计
### 6.1应用层设计目标
应用层中仅 `system_manager` 系统管理模块可调用 OSAL 接口，完成任务、定时器、内核资源的创建与全局调度；
其余业务应用模块（灯光控制、门锁控制、迎宾灯光等）仅调用服务层接口，**禁止直接访问 OSAL、驱动层与 HAL 库**
- 根据输入事件执行控制策略；
- 管理BCM运行状态；
- 控制执行器输出；
- 实现车辆功能逻辑；
- 触发状态反馈。

### 6.2 应用层软件结构
```
Application
├── bcm_state              // BCM状态管理模块
├── bcm_fault              // BCM故障管理模块
├── light_control          // 灯光控制模块
├── door_control           // 门锁控制模块
├── welcome_light          // 迎宾灯光模块
└── system_manager         // 系统状态管理模块
```
### 6.3 BCM状态管理模块（bcm_state）
#### 6.3.1 设计目的
统一维护 BCM 整机运行状态，集中管理灯光、门锁、工作模式、昼夜、故障等级等全局状态；避免多模块各自缓存状态造成数据不一致、跨任务直接读写全局变量引发数据竞争。外部模块**禁止直接操作结构体成员**，全部通过封装接口访问。
#### 6.3.2 状态数据结构
```
typedef struct
{
    uint8_t light_state;    // 灯光状态
    uint8_t door_state;     // 门锁状态
    uint8_t work_mode;      // 系统工作模式
    uint8_t night_state;    // 昼夜环境状态
    uint8_t fault_level;    // 故障等级
    uint8_t light_work_mode; // 灯光工作模式
}BCM_State;
```
模块内部私有静态变量 `static BCM_State bcm_state`，外部不可直接访问；配套静态互斥锁 `bcm_state_mutex`，用于多任务并发读写保护。
#### 6.3.3 接口设计
| 接口 | 功能说明 |
| --- | --- |
| `void BCM_State_Init(void);` | 模块初始化，创建互斥锁并重置所有状态初始值 |
| `void BCM_GetState(BCM_State *p_bcm);` | 获取状态快照，拷贝完整状态到外部传入缓冲区（只读读取） |
| `void BCM_SetLightState(uint8_t state);` | 设置灯光状态，入参做范围校验 |
| `void BCM_SetLockState(uint8_t state);` | 设置门锁状态，入参做范围校验 |
| `void BCM_SetWorkMode(uint8_t mode);` | 设置系统工作模式，入参做范围校验 |
| `void BCM_SetNightState(uint8_t night);` | 设置昼夜环境状态，入参做范围校验 |
| `void BCM_SetLightWorkMode(uint8_t mode);` | 设置灯光工作模式 |
| `void BCM_SetFaultLevel(uint8_t level);` | 设置系统故障等级 |
#### 6.3.4 访问规则
1. 全局状态结构体为模块私有，**外部禁止直接读写结构体成员**，只能调用本模块提供的 API。
2. 所有读写操作均使用 OSAL 静态互斥锁保护，锁等待方式为永久等待`OSAL_WAIT_FOREVER`，保证状态读取 / 修改的原子性。
3. `BCM_GetState`采用**快照拷贝**，读出后外部拿到的是副本，外部修改副本不会影响内部真实全局状态。
4. 状态写入接口增加入参合法性校验，非法参数直接丢弃，防止无效状态写入。
   
### 6.4 灯光管理模块（light_control）
#### 6.4.1 设计目的
实现车灯手动 / 自动模式管理，灯光输出控制、硬件回读校验、故障上报与 CAN 状态报文上报。
#### 6.4.2 状态数据结构
内部静态影子变量`light_shadow`，缓存上一次灯光输出状态，用于状态变化判断。
#### 6.4.3 接口设计

- `void LightControl_Init(void)`：灯光模块初始化，影子变量置为灯关闭
- `void LightControl_ToggleWorkMode(void)`：切换灯光手动 / 自动模式
- `uint8_t LightControl_GetWorkMode(void)`：获取当前灯光工作模式
- `void LightControl_SetOutput(uint8_t state)`：设置灯光目标输出状态
- `void LightControl_Toggle(void)`：翻转灯光开关状态
- `void LightControl_Process(void)`：周期处理函数，状态变化时触发诊断设置、CAN 报文发送
- `void LightControl_FeedFaultMgr(void)`：读取硬件回读信号，送入故障管理模块
#### 6.4.4 访问规则

1. 读取 BCM 全局状态必须调用`BCM_GetState`获取状态快照
2. 仅当灯光状态发生变化时，才执行 CAN 报文发送操作
3. 硬件触点回读增加 20ms 软件防抖；目标状态与回读不一致持续超时，上报灯光故障码 0x03
4. 按键、CAN 指令优先级高于自动迎宾时序，可直接接管灯光输出

### 6.5 车锁控制模块（lock_control）
#### 6.5.1 设计目的
实现车锁状态控制、按键 / CAN 指令处理、状态边沿检测、底层执行器下发、CAN 状态上报以及车锁硬件故障采集，与 BCM 全局状态模块联动。
#### 6.5.2 状态数据结构
内部静态变量：
- `last_lock_state`：上一周期车锁状态，用于边沿检测
- `unlock_flag`：解锁事件标记位
- `lock_shadow`：车锁状态影子变量，用于状态变化判断
#### 6.5.3 接口设计
- `void LockControl_Init(void)`：模块初始化，初始化影子变量，读取初始车锁状态
- `void LockControl_SetOutput(uint8_t state)`：CAN 指令入口，设置目标车锁状态
- `void LockControl_Toggle(void)`：按键指令入口，翻转当前车锁状态
- `void LockControl_Process(void)`：周期处理函数，边沿检测，状态变更时下发执行器、发送 CAN 报文
- `uint8_t LockControl_GetUnlock(void)`：查询本周期是否产生解锁事件
- `void LockControl_FeedFaultMgr(void)`：读取车锁硬件回读故障，送入故障管理模块
#### 6.5.4 访问规则
1. 读取 BCM 全局锁状态必须调用`BCM_GetState`获取状态快照，禁止直接访问全局状态变量
2. 使用影子变量`lock_shadow`，仅车锁状态发生变化时，才下发底层执行器并发送 CAN 状态报文
3. 通过`last_lock_state`做边沿检测，捕获上锁→解锁事件，置位解锁标记`unlock_flag`
4. 采集车锁硬件触点回读信号，将故障信息送入故障管理模块做故障判定

### 6.6 迎宾灯模块（welcome_light）
#### 6.6.1 设计目的
实现解锁触发迎宾灯光逻辑，满足模式、夜间环境等条件判断；自动控制迎宾灯启停，支持外部指令抢占终止迎宾时序。
#### 6.6.2 状态数据结构
内部静态变量：
- `welcome_running`：迎宾时序运行标记
- `welcome_start_ms`：迎宾启动时刻时间戳
#### 6.6.3 接口设计
- `void WelcomeLight_Init(void)`：模块初始化，清空运行标记与计时
- `static void WelcomeLight_RefreshNightState(void)`：更新夜间环境状态，读取滤波后的光照信号写入 BCM 全局状态
- `void WelcomeLight_OnUnlockEvent(void)`：解锁事件入口，校验触发条件，条件满足则启动迎宾灯光
- `void WelcomeLight_Process(void)`：周期处理函数（10ms 周期），监控迎宾运行状态，检测终止条件，超时自动关闭灯光
- `uint8_t WelcomeLight_IsRunning(void)`：查询迎宾时序是否正在运行
#### 6.6.4 访问规则
1. 读取 BCM 全局状态使用`BCM_GetState`获取状态快照，修改状态调用 BCM_Set 接口
2. 迎宾触发条件：解锁事件、灯光自动模式、夜间状态、当前灯光关闭；迎宾运行中收到新解锁事件直接忽略
3. 优先级规则：切换为手动模式、外部指令关闭灯光均可直接终止迎宾时序
4. 迎宾到达设定时长后，自动关闭灯光并结束时序
5. 夜间环境信号由信号滤波模块读取，更新至 BCM 全局夜间状态


### 6.7 故障管理模块（bcm_fault）
#### 6.7.1 设计目的
统一接收各业务模块上报故障事件，维护当前活跃故障表，分级计算系统故障等级；驱动故障指示灯、蜂鸣器告警，联动存储模块读写 Flash 故障日志，提供严重故障下执行器锁定判定。
#### 6.7.2 状态数据结
内部静态变量：
- `active_fault_table[4U]`：活跃故障表，保存传感器、CAN、灯光、门锁四类故障的当前事件状态
- `red_blink_en`：故障红灯闪烁使能标志
- `beep_blink_en`：蜂鸣器间歇鸣叫使能标志
- `fault_table_mtx`：故障表互斥锁，保护多任务并发读写故障数组
#### 6.7.3 接口设计
- `void BcmFault_Init(void)`：模块初始化，创建故障表互斥锁，清空活跃故障表，读取打印 Flash 历史故障日志
- `void BcmFault_ReceiveFaultEvent(FaultCode_t fault_code, FaultEventType_t event)`：接收故障事件，更新活跃故障表
- `void BcmFault_SetFaultLevel(void)`：扫描故障表，计算系统故障等级，写入 BCM 全局状态
- `uint8_t BcmFault_GetHeartBeatMode(void)`：查询是否存在故障，用于心跳报文状态填充
- `uint8_t BcmFault_SevereFaultLockActuator(void)`：严重故障判定，严重故障时锁定 CAN 侧执行器控制（本地按键不受限）
- `void BcmFault_ClearHistoryFault(void)`：清空内存活跃故障表，清除 Flash 中全部历史故障记录
- `void BcmFault_LedBeep_Control(void)`：根据故障等级设置 LED、蜂鸣器告警策略
- `void AlarmTimerCallback(void *pvArg)`：软件定时器回调，实现红灯闪烁、蜂鸣间歇鸣叫翻转
#### 6.7.4 访问规则
1. 故障表读写必须获取`fault_table_mtx`互斥锁，防止多任务抢占造成数据异常
2. 故障分级规则：CAN 故障判定为严重故障；传感器 / 灯光 / 门锁故障判定为普通故障；无故障则为正常等级
3. 告警逻辑：正常 - 常亮绿灯；普通故障 - 绿灯常亮 + 红灯闪烁；严重故障 - 绿灯熄灭 + 红灯闪烁 + 蜂鸣间歇鸣叫
4. 严重故障保护：CAN 指令禁止控制执行器，本地按键操作保留可用
5. 读写 Flash 故障日志调用存储管理模块接口，故障等级结果写入 BCM 全局状态

### 6.7 系统状态管理模块
任务创建、软件定时器管理、系统调度相关操作，均通过 OSAL 抽象接口完成，模块内部不直接调用 FreeRTOS 原生函数。
- **模式管理**：维护系统两种运行模式
  - 正常模式：所有功能正常运行，RGB绿灯常亮
  - 故障模式：执行器全部断开，严重故障声光报警，保留本地按键与故障清除功能
- **上电自检**：上电依次完成时钟、GPIO、ADC、CAN、串口、Flash外设自检；自检失败直接进入故障模式
- **心跳管理**：周期上报设备心跳报文（ID:0x100），报文中携带当前系统工作模式
- **故障联动**：严重故障产生时自动切入故障模式；所有严重故障消除后恢复正常模式

## 7 FreeRTOS任务与调度设计
**本章节为系统调度模型设计，底层基于 FreeRTOS 实现；所有任务、队列、定时器的内核对象操作，统一通过 OSAL 抽象接口完成，上层业务代码不直接使用 FreeRTOS 原生 API。**
### 7.1 任务总表
| 任务名称       | 优先级 | 周期/触发   | 主要职责                 |
| -------------- | ------ | -----------| ---------------------- |
| CAN协议任务    | 5      | Queue阻塞   | CAN解析、协议处理                |
| 故障监控任务   | 4      | 10ms周期    | 故障检测、防抖                   |
| 输入采集任务   | 3      | 10ms周期    | ADC采集、按键扫描                |
| BCM控制任务    | 3      | 事件触发    | 灯光、门锁、迎宾逻辑             |
| 系统管理任务   | 2      | 50ms周期    | 模式管理、心跳、看门狗           |
| 故障处理任务   | 1      | 事件触发    | Flash写入、日志输出、故障上报报文 |
### 7.2 软件定时器配置
周期报文由FreeRTOS软件定时器驱动，不受任务阻塞影响，保障时序容差指标。

| 定时器名称 | 周期 | 回调函数职责 |
| --- | --- | --- |
| 心跳报文定时器 | 2000ms | 置位心跳发送标志，触发心跳报文发送 |
| 声光报警定时器 | 500ms | 控制报警 LED、蜂鸣器翻转，实现间歇声光告警 |

### 7.3 任务间通信机制
1. **消息队列**
   - CAN接收队列：CAN中断投递原始报文，接收任务读取解析
   - 指令队列：解析后的控制指令投递至执行器任务
   - 故障事件队列：故障检测模块投递故障事件，触发上报与存储
2. **互斥锁**
   - 全局状态互斥锁：保护 BCM 整机全局状态结构体，多任务读写状态快照
   - 故障表互斥锁：保护活跃故障表，故障事件更新、故障等级计算时防数据竞争
   - 看门狗服务互斥锁：保护任务心跳计数数组，用于多任务上报心跳与巡检
   - CAN 发送互斥锁：保护 CAN 报文发送接口，避免多任务并发发送造成报文错乱
   - Flash 操作互斥锁：保护 Flash 读写与 SPI 总线，防止并发访问 Flash
   - 串口打印互斥锁：保护日志输出，防止多任务同时打印导致日志乱码
3. **访问规则**：多任务共享变量必须通过临界区或互斥锁保护，禁止无保护并发读写

### 7.4 时序指标保障
严格匹配 CAN 通信协议时序规范：
- 状态变化事件报文：状态变更后 ≤20ms 完成发送
- 故障从原始异常采样到故障防抖确认最大 200ms；故障确认完成后，故障报文上报 ≤50ms
- 指令响应：CAN 报文解析运算耗时 ≤5ms（不含任务调度等待），指令输出动作执行完成 ≤50ms；包含继电器触点稳定与回读校验的状态反馈报文 ≤100ms

## 8 核心业务流程
### 8.1 上电启动流程
1. 系统复位，HAL库初始化，系统时钟配置为72MHz
2. 外设驱动依次初始化：GPIO、ADC、CAN、UART、SPI、IWDG
3. FreeRTOS内核初始化，创建所有任务、队列、定时器、互斥锁
4. 加载Flash历史故障记录，初始化故障管理模块
5. 启动系统调度器，任务开始运行
6. 完成上电自检，自检通过进入正常模式；失败进入故障安全模式
7. 存在历史故障则上电首次上报故障状态报文

### 8.2 CAN控制指令处理流程
1. CAN外设收到报文，触发接收中断，将原始帧写入CAN接收队列
2. CAN接收任务被唤醒，读取报文并执行协议校验
3. 校验不通过：直接丢弃，记录错误日志
4. 校验通过：解析指令内容，投递至执行器控制任务
5. 执行器任务进行优先级仲裁，高优先级指令覆盖当前低优先级动作
6. 更新继电器输出电平，延时稳定后读取触点回读，校验执行结果
7. 状态发生变化时，触发对应状态报文上报；校验失败则触发故障上报

### 8.3故障检测与处理流程
1. 各服务层、应用层模块实时检测自身对应的异常条件，检测到状态变化时主动上报原始异常状态至故障管理模块；
2. 故障管理模块接收上报的原始状态，对每一路故障独立启动防抖计时，瞬时抖动会自动清零防抖计数；
3. 持续异常达到防抖判定时间，确认故障激活：
   - 更新全局故障状态位图；
   - 组装故障激活事件投递至故障事件队列，系统任务读取队列后触发 CAN 故障报文（ID:0x61）上报；
   - 存储模块读取故障事件，将故障记录写入 Flash 故障日志；
   - 系统管理模块根据故障等级执行对应安全策略、声光报警逻辑。
4. 模块上报状态恢复正常时，故障管理模块启动故障恢复防抖计时；
5. 持续正常达到恢复防抖阈值，确认故障消除：
   - 更新全局故障状态位图；
   - 生成故障消除事件，上报 CAN 故障消除报文；
   - 系统遍历当前所有激活故障，无严重故障后自动退出故障安全模式。

### 8.4 灯光控制与迎宾灯光流程
1. 传感器任务周期采集光照ADC值，经滑动滤波后输出有效值
2. 滞回比较算法判定昼夜状态，状态变更时更新全局光照标志
3. 灯光管理模块判断当前模式：
   - 手动模式：仅通过本地按键、CAN 总线指令控制灯光状态
   - 自动模式：开启迎宾灯功能
4. 门锁解锁事件触发时：
   - 判定当前为黑夜则启动迎宾灯光，点亮车灯
   - 启动迎宾软件定时器，计时期间暂停自动灯光逻辑
   - 计时结束后恢复原灯光模式与自动控制逻辑

## 9 异常与可靠性设计
### 9.1 故障状态
系统进入故障模式时，强制执行以下状态：
- 所有继电器输出低电平，负载全部断开
- RGB红灯常亮，绿灯强制熄灭
- 蜂鸣器按严重故障节奏报警
- 保留本地按键功能与故障清除能力
- 周期心跳报文继续发送，工作状态字段更新为故障模式（0x01）

### 9.2 CAN总线异常处理
严格对齐CAN协议规范定义的三级错误状态与恢复流程：
- **主动错误状态**：TEC<127且REC<127，正常通信，无额外处理
- **被动错误状态**：TEC≥127或REC≥127，记录轻微故障，继续通信
- **总线关闭（Bus‑Off）**：
  1. 记录CAN总线严重故障（故障码0x02），执行器切入安全状态
  2. 尝试发送故障状态报文；总线无法发送时存入本地故障缓存
  3. 延时100ms后完整重新初始化bxCAN外设，清除错误计数器
  4. 初始化成功后恢复通信，上报故障消除报文
  5. 最多连续重试3次，失败则保持故障模式，等待系统复位

### 9.3 看门狗防护
- 独立看门狗溢出时间约2s，由系统状态任务统一喂狗
- 任务卡死、程序跑飞、硬fault等异常场景触发看门狗自动复位
- 复位后系统记录看门狗复位事件，便于问题追溯

### 9.4 数据可靠性
- Flash故障记录增加校验和，读取时校验完整性
- 全局共享资源全部加锁保护，避免多任务并发读写错乱
- 指令与故障均采用防抖机制，滤除瞬时干扰与误触发
